# LighterPack Product Philosophy

本文档是新增需求进入计划前的宏观评审清单。目标是约束产品复杂度，优先发布能改善核心工作流的改动，尽快获得真实用户反馈。

## 产品定位

LighterPack 是一个结构化装备清单和重量决策工具。

它不是装备推荐商城、社交社区、旅行内容平台或通用项目管理工具。核心价值是帮助用户快速录入装备，理解重量结构，复用已有装备，并把清单分享给他人检查或讨论。

## 核心产品内核

用最少的结构化输入，换取对装备重量结构的持续可见性。

用户应该能回答这些问题：

- 我这次实际要背多重？
- 重量主要集中在哪些分类？
- 哪些是穿戴重量，哪些是真正背包重量？
- 哪些是消耗品？
- 哪些装备最值得优先优化？
- 这份清单能否被复用、分享和讨论？

## 优先级原则

| 优先级 | 方向 | 判断标准 |
| --- | --- | --- |
| P0 | 录入速度 | 是否让用户更快把真实装备录入系统 |
| P1 | 重量判断 | 是否让用户更清楚地理解和优化重量 |
| P2 | 复用能力 | 是否减少重复录入，提升装备库价值 |
| P3 | 分享输出 | 是否让清单更适合被他人阅读、检查和传播 |
| P4 | 未来扩展 | 是否为旅行计划、规则推荐或 AI 推荐提供必要数据基础 |

不满足 P0-P3 中至少一项的需求，默认不进入近期计划。

## 标签系统原则

Tag 的目标是提升装备复用能力，而不是让用户维护另一套复杂分类。

- Category 是当前清单的组织方式，tag 是装备本体的长期记忆；两者可以互相启发，但不应永久绑定。
- 系统可以用 category name 提供安静的默认 tag，但不能覆盖用户已经表达过的 tag 意图。
- Tag 行为应优先采用自动补偿、可见可编辑的轻交互，避免在高频录入路径上弹窗打断。
- 空 tag 是合法状态；未分类装备仍然应该可以正常录入、统计、保存、分享和复用。
- 未来更复杂的 tag 能力，例如来源追踪、批量应用或标准 GearType，应建立在真实使用反馈和清晰数据边界之上。

## 需求评审清单

每个新增需求进入 `docs/modernization-plan.md` 前，先回答：

1. 这个需求服务的是录入、判断、复用、分享中的哪一个核心动作？
2. 它能否在不增加主要流程复杂度的情况下落地？
3. 它是否改变 saved library JSON？如果改变，兼容和升级路径是什么？
4. 它是否能用现有 Vue 2、Vuex、Express 架构小步实现？
5. 它是否有明确验收标准和可测试的业务逻辑？
6. 它是否会让新用户更困惑？如果会，是否有更轻的设计？
7. 它是否必须现在做，还是可以等第一批用户反馈后再做？

只有答案清晰的需求才进入计划。

## 功能取舍规则

优先做：

- 快速录入和键盘操作。
- 更清楚的重量摘要和高重量项定位。
- 装备库筛选、标签和复用能力。
- 简洁、可分享、可导出的清单结果。
- 可测试的数据边界。

谨慎做：

- 大规模视觉重设计。
- 社交 feed、内容社区、复杂账号体系。
- 需要全量重写才能落地的功能。
- 先于结构化数据的 AI 推荐。
- 不能明显改善核心工作流的设置项。

## 发布策略

产品改进应遵循小步发布：

1. 先改善当前工作流。
2. 每次只引入一个可验证能力。
3. 每个能力都有明确验收标准。
4. 发布后观察真实用户是否使用。
5. 根据反馈决定继续增强、简化或删除。

当前阶段的目标不是堆叠功能，而是尽快把核心体验提升到可发布、可反馈、可迭代的状态。

## Beta Feedback Strategy

发布前反馈入口优先采用低风险静态方案：在产品内展示反馈邮箱和邮件提示，让用户主动发送问题描述、截图、清单分享链接、浏览器和设备信息。

当前阶段不内建反馈表单、不上传截图、不新增后端反馈接口、不自动发送邮件。原因是 beta 发布前更重要的是降低发布风险和尽快收集真实反馈，而不是引入新的邮件服务、反垃圾、防滥用或工单管理复杂度。

后续如果反馈量上升，再评估结构化反馈能力，例如 Bug/建议类型、当前 URL、user agent、登录用户、清单链接、邮件发送、数据库存储或外部工单系统集成。
