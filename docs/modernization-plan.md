# LighterPack Modernization Plan

本文档用于持续跟踪 LighterPack 的现代化、可维护性和功能演进计划。每次进入较大改动前，先更新这里的目标、边界和验收标准。

## 目标

1. 让现有项目在现代本地开发环境中稳定运行，降低维护成本。
2. 修复当前装备录入体验中的明显问题，尤其是空输入、自动创建无效分类或装备的问题。
3. 建立清晰的装备分类体系，让装备可以按类型、分组和场景被复用。
4. 为后续旅行计划和 AI 装备推荐做数据结构和接口准备。

## 非目标

- 第一阶段不做全量重写。
- 第一阶段不迁移到 Python 后端，除非现有 Node 后端阻碍基础维护。
- 第一阶段不引入 AI 功能，只为 AI 功能整理数据边界和测试基线。
- 不在没有测试保护的情况下大规模重写 `client/dataTypes.js` 或 Vuex store。

## 工程边界

### 前端边界

- 保留 Vue 2 作为当前运行基线。
- 新功能优先放在现有组件和 Vuex 结构内，避免一次性迁移框架。
- 减少隐式全局依赖，例如 `window.bus`、`window.router`、全局工具函数，但采用逐步替换策略。
- 所有影响保存数据结构的 UI 改动必须同步更新数据模型和测试。

### 后端边界

- 短期保留 Express API 和 MongoDB 文档存储。
- 后端接口先做输入校验、鉴权和错误处理改进。
- 数据结构稳定后，再评估迁移到 Python 后端，例如 FastAPI + SQLite/PostgreSQL。
- 后续 Python 后端应以清晰实体为核心：User、Library、List、Category、GearItem、GearType、TripPlan。

### 数据边界

当前核心模型：

| Entity | 当前位置 | 职责 |
| --- | --- | --- |
| `Library` | `client/dataTypes.js` | 用户装备库总容器 |
| `List` | `client/dataTypes.js` | 一份装备清单 |
| `Category` | `client/dataTypes.js` | 清单内分组 |
| `Item` | `client/dataTypes.js` | 装备本体 |
| `categoryItem` | `Category.categoryItems` | 装备在某个分类中的数量、穿戴、消耗状态 |

后续目标模型：

| Entity | 职责 |
| --- | --- |
| `GearItem` | 可复用装备本体，例如帐篷、炉具、雨衣 |
| `GearType` | 装备类型，例如 shelter、sleep、cook、clothing |
| `GearGroup` | 用户自定义分组，例如冬季徒步、摄影、轻量化 |
| `PackingList` | 某次实际携带清单 |
| `TripPlan` | 旅行计划，包括地点、天数、天气、强度、人数 |
| `Recommendation` | AI 或规则系统生成的装备建议 |

## 项目风格约定

| 方向 | 约定 |
| --- | --- |
| 改动方式 | 小步提交，每次改动有明确验收标准 |
| 兼容性 | 不破坏现有 saved library JSON，数据结构变化必须提供升级路径 |
| 测试 | 先补核心业务单元测试，再做大规模重构 |
| UI | 优先修复实际工作流，不做纯视觉重设计 |
| API | 新接口要有输入校验、错误返回和鉴权边界 |
| 文档 | 重要决策写入 `docs/`，避免只留在对话中 |
| 命名 | 用业务名表达含义，例如 `GearType` 优于模糊的 `Type` |
| 追溯 | 每次改动必须在 `docs/change-log.md` 中关联目标、记录验证方式和 commit |
| 提交 | 每个小功能点独立 commit，避免把无关变更混入同一个提交 |

## 阶段计划

| 阶段 | 名称 | 目标 | 主要任务 | 验收标准 |
| --- | --- | --- | --- | --- |
| 0 | 维护基线 | 让项目稳定可运行、可检查 | 修复现代 Node 构建问题；补 README；加入本地配置样例；整理 npm scripts | `npm run check` 通过，README 可按步骤启动 |
| 1 | 工程硬化 | 在大改前建立保护网 | 增加非破坏性 lint/check 脚本；给 `dataTypes.js` 增加单元测试；梳理核心数据 fixtures | 核心重量、数量、删除、复制、保存/加载逻辑有测试 |
| 2 | 空输入和自动创建修复 | 修复无效装备/分类被创建或保存 | 调查新增 item/category 的触发路径；阻止空分类、空装备进入有效数据；优化删除/取消空行体验 | 添加空装备不会污染统计、保存数据或分享页 |
| 3 | 装备分类体系 | 支持按装备类型和分组管理装备 | 设计 `GearType`/`GearGroup`；给装备增加类型字段；提供筛选和拉取入口；兼容旧数据 | 用户可以按类型查找并添加装备到清单 |
| 4 | 清单体验优化 | 让网页更适合长期使用 | 优化列表、分类、装备编辑流程；改善移动端和密集数据展示；减少误操作 | 常用编辑流程更少点击，关键状态清晰 |
| 5 | 后端接口整理 | 为后续 Python 迁移做准备 | 定义 API contract；增加请求校验；拆分认证、library 保存、分享接口 | API 行为明确，有测试或文档覆盖 |
| 6 | 旅行计划模型 | 引入旅行计划但不急于 AI | 建立 TripPlan 数据结构；支持目的地、时间、人数、活动类型、天气备注 | 用户可以创建旅行计划并关联装备清单 |
| 7 | AI 推荐准备 | 让 AI 推荐基于结构化数据 | 设计推荐输入格式；实现规则版推荐 baseline；记录用户接受/拒绝反馈 | 无 AI 时也有可解释推荐结果 |
| 8 | AI 装备推荐 | 引入 AI 生成装备建议 | 接入模型；基于 TripPlan、GearItem、历史清单生成建议；展示理由和风险提示 | AI 建议可被用户审查、修改、加入清单 |

## 第一批任务拆解

### Task 0.1: 维护基线

状态：完成

内容：

- 修复现代 Node.js 下 Webpack 构建问题。
- 增加 `npm run check`。
- 增加 `npm run test:e2e`。
- 增加 `config/local.example.json`。
- 更新 README。

验收：

- `npm run check` 成功。
- README 能指导新开发者启动项目。

### Task 1.1: 测试工具选择

状态：完成

建议：

- 单元测试优先覆盖纯业务逻辑，不依赖浏览器。
- 优先测试 `client/dataTypes.js` 和 `client/utils/weight.js`。
- 如果保持当前依赖，可以先用 Node 内置 `node:test`，避免立刻引入大型测试框架。

验收：

- 能运行一个稳定的单元测试命令。
- 测试失败能准确指出业务逻辑问题。

实现：

- 使用 Node 内置 `node:test`，避免新增测试依赖。
- 使用 `npm run test:unit` 运行单元测试。
- `npm run check` 同时运行单元测试和生产构建。

### Task 2.1: 空输入和自动创建行为调查

状态：完成

需要确认的路径：

- 新建列表时是否应该自动创建一个分类和一个空装备。
- 新建分类时是否应该自动创建一个空装备。
- 新建装备时是否会意外创建分类。
- 空装备、空分类是否会进入保存数据、统计、分享页和 CSV。

验收：

- 明确哪些自动创建行为应该保留，哪些应该删除。
- 写出行为表，并用测试固定下来。

当前行为：

| 路径 | 当前行为 | 问题 | 决策 |
| --- | --- | --- | --- |
| `Library.firstRun()` | 新用户默认创建 1 个 list、1 个 category、1 个空 item | 空 item 会进入保存数据和数量统计 | 保留 UI 起步体验，但空 item 不应算作有效装备 |
| Vuex `newList` | 新建 list 后自动创建 1 个 category、1 个空 item | 空 list 也会携带无效 item | 保留起步占位结构，但保存和统计应忽略空 item |
| Vuex `newCategory` | 新建 category 后自动创建 1 个空 item | 空 category 会携带无效 item | 保留快速录入体验，但保存和输出应过滤空 item |
| Vuex `newItem` | 只在当前 category 中创建空 item | 不会额外创建 category | 保留 |
| `Category.calculateSubtotal()` | 所有 category item 都计入 `subtotalQty` | 空 item 默认 `qty: 1`，污染数量统计 | 空 item 不参与数量、重量、价格统计 |
| `Library.save()` | 保存所有 items/categories/lists | 空 item 会进入 localStorage/MongoDB | 保存时过滤无意义空 item，并清理 category 引用 |
| 分享页/嵌入页 | 渲染所有 category item | 可能输出空装备行 | 依赖保存过滤和渲染侧保护 |
| CSV 导出 | 输出所有 category item | 可能输出空 CSV 行 | 跳过空 item |

空 item 定义：

一个 item 同时满足以下条件时视为无意义空 item：

- `name`、`description`、`url`、`image`、`imageUrl` 均为空白。
- `weight` 为 0。
- `price` 为 0 或未设置。

这种 item 可以临时存在于编辑 UI 中作为占位输入，但不应污染统计、保存数据、分享页或 CSV。

### Task 2.2: 空输入修复

状态：待开始

原则：

- 空白 placeholder 可以存在于 UI，但不应被当成有效装备。
- 保存前应过滤或阻止无效空实体。
- 删除最后一个分类或装备时，要给用户可理解的空状态，而不是制造隐藏数据。

验收：

- 输入为空的装备不参与总重、价格、数量统计。
- 分享页和 CSV 不输出空装备。
- 保存数据中不包含无意义空装备，或至少有明确兼容策略。

## 当前风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 旧依赖较多 | 新 Node 或浏览器环境可能出现兼容问题 | 先固定可运行脚本，再逐步升级 |
| 数据模型集中在前端 | 后端难以校验数据正确性 | 先补测试，再提取 schema 和 API contract |
| 自动保存隐藏错误 | 空数据或错误数据容易被保存 | 增加保存前校验和测试 |
| 分享页服务端渲染重复逻辑 | 前后端统计可能不一致 | 用共享测试 fixtures 验证结果 |

## 每阶段完成定义

一个阶段只有满足以下条件才算完成：

1. 相关功能有明确验收标准。
2. 核心逻辑有测试或手动验证记录。
3. README 或 `docs/` 中记录了开发者需要知道的变化。
4. 没有引入未解释的数据结构兼容性风险。
5. `npm run check` 通过。
